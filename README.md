# Career OS

나의 경험을 다음 기회로 연결하는 한국어 개인 커리어 워크스페이스입니다. **Phase 1~4를 구현했습니다.** 로그인, 서버 DB, 유료 API 없이 브라우저에 데이터를 저장합니다.

## 구현한 기능

- 프로필 생성·조회·수정·삭제: 연락처, 희망 직무, 소개, 핵심역량, 기술스택, 링크
- 경력 CRUD: 회사·부서·직책·재직 기간·담당업무·성과
- 프로젝트 CRUD: 경력 연결, 기간, 역할, 참여 인원, 기술, 문제·목표·기여·설계·기술 선택·해결 과정·성과·회고·자료 링크
- 프로젝트 검색, 진행 상태 필터, 상세 보기
- 실제 저장된 기록으로 계산하는 대시보드, 최근 프로젝트, 기록 점검
- IndexedDB 영속 저장, 다른 탭의 변경 반영, 입력 검증 및 저장 오류 안내
- JSON 백업 다운로드, 파일 검증, 교체 확인, 트랜잭션 기반 복원
- 반응형 레이아웃, 키보드 탐색, 대화상자 포커스 관리, 삭제·미저장 변경 확인
- GitHub Pages용 HashRouter, `/career-os/` base, 검사 후 배포 워크플로
- 기업·직무별 이력서 생성·복제·삭제, 초안 자동 저장과 저장 상태 표시
- 원본과 분리된 문구 편집, 경력·프로젝트·성과 선택, 순서 변경, 섹션 표시·숨김
- 학력·자격증·수상·외국어 입력, 이력서/경력기술서 형식 선택
- 한글 A4 다중 페이지 미리보기, 확대·축소, 모바일 편집/미리보기 전환, 브라우저 인쇄/PDF 저장
- 읽기 전용 저장 버전·제출본, 현재 초안·이전 버전·최신 원본 비교, 스냅샷에서 새 초안 생성
- 누락·기간·역할·기술·성과 근거·링크·설명 길이 규칙 점검, 오류가 있는 제출본 확정 방지
- 채용공고 카드/표, 검색·직무·기술·즐겨찾기 필터, 마감일 정렬, 중복 공고 안내
- JD 원문과 요구사항 구조화, 규칙 기반 기술 표기 정규화, 사용자가 검토하는 프로젝트 근거 연결
- 선택 정보만 포함하는 ChatGPT 프롬프트 5종, 전체 미리보기·민감정보 확인 후 복사, 수동 분석 결과 버전·비교
- 지원 칸반/테이블, 드래그 및 선택창 단계 변경, 변경 이력, 기업별 맞춤 초안 연결·복제
- 지원별 독립 제출 증빙, 원본 이력서 삭제 후에도 문서 확인/PDF, 외부 제출 구분
- 날짜·시간을 구분하는 일정/후속 조치, 마감 D-day, 실제 이력 기반 지원 통계
- JD·지원·프로젝트·제출본 복사본으로 면접 준비, 규칙 기반 예상 질문, 질문 은행·즐겨찾기·복습 필터
- STAR·자유 답변·핵심 요약 자동 저장, 불변 답변 버전·최신 지정·비교, 자체 점검 체크리스트
- 모의 면접 질문별 진행·시간 측정·꼬리질문·중단/이어하기·피드백, 실제 면접 회고 구분
- 선택 자료만 포함하는 ChatGPT 면접 프롬프트 6종과 수동 분석 보관
- 포트폴리오 독립 초안·상세 프로젝트 편집·순서·이미지·공개 미리보기
- 공개 섹션/경력/프로젝트/이미지 승인, 최종 JSON 확인, 정적 ZIP 내보내기, 독립 공개 페이지

기본 예시 데이터는 넣지 않았습니다. 통계는 빈 저장소에서 0으로 시작합니다. 테스트의 가상 데이터는 프로덕션 앱에 포함되지 않습니다.

## 기술 스택

React 19, Vite 8, TypeScript 6, Tailwind CSS 4, React Router 7, Lucide Icons, Dexie 4 + IndexedDB, Zod 4를 사용합니다. 공통 UI는 shadcn/ui의 로컬 소스 관리 방식에 맞춘 Radix Dialog/Slot + CVA 컴포넌트입니다. 외부 템플릿이나 유료 UI 서비스는 필요하지 않습니다. ESLint, Prettier, Vitest, fake-indexeddb, Playwright, axe-core로 검증합니다.

정확한 의존성 버전은 `package-lock.json`에 고정됩니다. 개발 도구의 `minimatch`에는 취약점 [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249)의 수정 버전을 적용하는 override가 있습니다. 향후 상위 패키지에서 수정 버전을 채택하면 제거할 수 있습니다.

한글 PDF의 일관성을 위해 OFL 라이선스의 Noto Sans KR을 앱에 포함합니다. 외부 폰트 서버에 요청하지 않습니다. 라이선스는 `public/licenses/noto-sans-kr.txt`에 있습니다. PDF 생성은 무료 브라우저 인쇄 기능을 사용하며, `pdf-lib`는 테스트에서 실제 PDF 페이지 수와 A4 크기를 검사하는 개발 의존성으로만 사용합니다.

## 설치 및 실행

Node.js **22.18 이상인 22.x 또는 24 이상**과 npm이 필요합니다. CI는 Node 24를 사용합니다. 아래 명령어는 Windows PowerShell용입니다. `npm.ps1` 실행 정책을 변경할 필요 없이 `npm.cmd`를 사용합니다.

```powershell
Set-Location 'D:\personal_project\career-os'
npm.cmd ci
npm.cmd run dev
```

개발 주소: <http://127.0.0.1:5173/career-os/>. 포트가 사용 중이면 터미널에 표시된 주소를 사용하세요. 다른 운영체제에서는 `npm.cmd` 대신 `npm`, `npx.cmd` 대신 `npx`를 사용합니다.

```powershell
npm.cmd run typecheck
npm.cmd run lint
npm.cmd test
npm.cmd run build
npx.cmd playwright install chromium
npm.cmd run test:e2e
npm.cmd run preview
```

프로덕션 미리보기: <http://127.0.0.1:4173/career-os/>. E2E 테스트 전에 반드시 빌드하세요. 테스트는 이 포트의 미리보기 서버를 자동으로 실행하고 종료합니다. 이미 해당 주소에서 프로젝트 미리보기가 실행 중이면 재사용합니다.

`npm.cmd run format`은 코드 정리, `npm.cmd run format:check`는 서식 검사입니다. Playwright는 일회성 테스트 브라우저 프로필을 사용하며 사용자가 입력한 브라우저 데이터를 건드리지 않습니다. `test-results/`, `playwright-report/`는 Git 제외 대상입니다.

## 데이터 구조와 Migration

**별도 Migration 명령어 불필요.** Phase 4 앱을 열면 Dexie가 `career-os` DB를 v4로 자동 업그레이드합니다. v1·v2·v3의 테이블·인덱스·행을 유지하고 신규 테이블만 추가합니다. 이전 버전에서 바로 열어도 중간 단계의 테이블이 함께 생성됩니다. 기존 JSON 백업을 보관한 뒤 업데이트된 앱을 여세요. 개발 검증에는 격리된 가상 DB와 일회성 브라우저 프로필만 사용했습니다.

| 테이블            | 내용                                               | 키와 관계                                |
| ----------------- | -------------------------------------------------- | ---------------------------------------- |
| profiles          | 개인 프로필 1개                                    | `id = profile`                           |
| careers           | 경력                                               | UUID                                     |
| projects          | 프로젝트와 문제 해결 기록                          | UUID, 선택적 `careerId → careers.id`     |
| settings          | 마지막 백업 다운로드 요청 시각                     | `id = settings`                          |
| resumes           | 원본과 독립된 편집 가능한 초안, 학력·자격·언어     | UUID, 충돌 방지용 `revision`             |
| resumeVersions    | 저장 버전과 제출본 전체 문서 스냅샷                | UUID, `resumeId`, 이력서별 고유 `number` |
| jobs              | 채용공고, 요구사항, 근거, 수동 분석                | UUID, 충돌 방지용 `revision`             |
| applications      | 지원 정보, 단계 이력, 독립 제출 증빙               | UUID, `jobId`, `revision`                |
| events            | 지원별 일정과 완료 여부                            | UUID, `applicationId → applications.id`  |
| preparations      | 준비 당시 JD·근거·프로젝트·경력·제출본·일정 복사본 | UUID, 원본 ID는 역사적 출처              |
| questions         | 질문·STAR 초안·불변 답변 버전·최신 지정            | UUID, `preparationId`, `revision`        |
| sessions          | 질문/답변 복사본·시간·꼬리질문·피드백·회고         | UUID, `revision`                         |
| interviewAnalyses | 수동 면접 분석 결과와 선택 당시 프롬프트           | UUID, `preparationId`                    |
| portfolios        | 독립 초안·공개 선택·승인 당시 정적 데이터 이력     | UUID, `revision`                         |
| portfolioAssets   | 메타데이터를 제거한 이미지 Blob                    | UUID, `portfolioId`, JSON 백업 제외      |

주요 기록에 `createdAt`·`updatedAt`을 ISO 형식으로 저장합니다. 기간은 `YYYY-MM`이며 진행 중인 항목의 종료일은 빈 문자열입니다. 경력 삭제는 연결된 프로젝트를 삭제하지 않고 `careerId`만 해제합니다. 저장과 관계 변경은 데이터 계층에서 수행합니다. 향후 동기화나 AI 기능을 추가할 때 UI와 데이터/분석 계층을 분리하여 확장할 수 있습니다.

초안의 경력·프로젝트는 원본 식별자와 문구의 복사본을 저장합니다. 원본 수정·삭제는 이미 만든 초안과 버전에 자동 반영되지 않습니다. 작성기의 원본 다시 불러오기는 확인 후 현재 초안의 프로필·경력·프로젝트만 교체합니다. 버전은 생성만 가능하며 편집 API가 없습니다. 이력서를 삭제하면 해당 이력서의 버전도 삭제되므로 확인창에서 안내합니다. 다른 탭에서 같은 초안이 먼저 수정되면 오래된 저장을 거절합니다.

`jobs`에는 요구사항·프로젝트 근거 복사본·수동 분석 버전을 함께 저장합니다. `applications`에는 생성 당시 공고 정보·단계 이력·제출 증빙을 저장하며 같은 공고에 재지원하면 별도 ID를 만듭니다. `events`는 지원 ID에 연결됩니다. 단계 변경과 이력 저장은 단일 트랜잭션입니다. 공고를 삭제하면 지원의 `jobId`를 해제하고 공고 복사본은 보존합니다. 지원 기록을 삭제하면 해당 이력·증빙·일정을 함께 삭제하므로 확인을 받습니다.

확인한 근거의 프로젝트 ID와 제출 문서의 원본 이력서/버전 ID는 **역사적 출처**입니다. 원본이 삭제되어도 독립 복사본으로 유효합니다. 화면은 삭제된 원본으로 편집 링크를 만들지 않으며 보관한 근거와 문서를 표시합니다. 원본 프로젝트 수정은 확인된 근거를 바꾸지 않습니다. 요구사항 문장·구분을 바꾸면 근거 상태를 확인 필요로 되돌립니다.

백업은 v4로 생성하며 v1·v2·v3·v4 복원을 지원합니다. 알 수 없는 버전은 거절합니다. v4 백업은 이전 Phase 앱에서 복원할 수 없습니다. 질문과 세션은 원본 삭제 후에도 복사본을 유지합니다. 질문 삭제는 해당 답변 버전도 삭제하지만 세션에 보관한 질문·답변은 보존합니다. 세션 저장과 복습 표시 추가는 단일 트랜잭션이며 질문·답변·세션·포트폴리오는 `revision`으로 다른 탭의 오래된 저장을 거절합니다.

## JSON 백업 및 복원

1. **설정 및 백업 → JSON 백업**을 눌러 다운로드합니다. `career-os-backup-날짜.json` 파일이 실제로 저장됐는지 확인하세요.
2. **파일 선택**에서 기존 백업을 선택합니다. 파일 크기(최대 20MB), JSON 형식, 버전, 필드, ID 중복, 연결 관계, URL, 기간, 단계 이력을 먼저 검사합니다.
3. 대화상자에서 백업 기록 수와 현재 기록 수를 비교합니다. 현재 데이터를 먼저 백업하고 **백업으로 교체**를 누르면 전체 데이터를 교체합니다. 병합 기능은 없습니다.
4. 잘못된 파일이나 복원 중 저장 오류가 발생하면 기존 기록은 유지됩니다. 쓰기 오류 시 전체 트랜잭션을 롤백합니다.

v4 백업에는 기존 기록과 `data.preparations`, `data.questions`, `data.sessions`, `data.interviewAnalyses`, `data.portfolios`를 포함합니다. 답변 버전·피드백·공개 선택·승인 당시 데이터도 함께 보관합니다. 복원은 전체 검증 후 모든 테이블을 단일 트랜잭션으로 교체합니다. 마지막 백업 요청 시각은 기기별 운영 정보라 백업하지 않으며 복원 시 초기화됩니다. 다운로드 성공 여부는 브라우저가 알려주지 않으므로 화면에는 **다운로드 요청 시각**으로 표시합니다.

**v1에는 이력서가 없고, v1·v2에는 Phase 3 기록이 없으며, v1~v3에는 면접·포트폴리오 기록이 없습니다.** 이전 백업을 복원하면 해당 신규 기록은 빈 컬렉션으로 교체됩니다. 확인창에서 삭제 영향을 명시적으로 경고하며 현재 데이터를 먼저 v4로 백업할 수 있습니다. 모든 버전의 JSON 복원은 현재 이미지 Blob도 제거합니다. 이미지 별도 백업을 먼저 받고 복원 후 다시 연결하세요. 실패 시 이미지 포함 전체 트랜잭션을 롤백합니다.

제출 증빙과 분석 원문을 함께 저장하므로 한도를 5MB에서 20MB로 늘렸습니다. 읽기 전 파일 크기와 내보낼 UTF-8 크기를 모두 확인합니다. JSON 파싱·검증 중에는 여러 객체 사본이 메모리에 존재하므로 무제한 파일을 허용하지 않습니다. 브라우저 저장 한도는 별개이며 용량 초과/쓰기 실패 시 현재 데이터는 유지됩니다.

## 이력서 작성과 출력

1. **이력서 작성 → 새 이력서 만들기**에서 현재 원본의 복사본을 만듭니다. 수정 사항은 잠시 입력을 멈추면 자동 저장되며, 미완성 문구도 초안으로 저장됩니다.
2. 경력·프로젝트 체크박스와 위/아래 버튼으로 포함 항목과 순서를 정합니다. 회사에 연결된 프로젝트는 해당 회사 아래 표시됩니다. 학력·자격·외국어는 이력서별로 입력합니다.
3. 작성 점검에서 오류와 권장사항을 확인합니다. **버전 저장**은 작성 중인 문서도 보관하며, **제출본 확정**은 오류를 고친 뒤 확인창을 거쳐 불변 스냅샷을 만듭니다. 이 기능은 외부 기업에 문서를 전송하지 않습니다.
4. 버전 선택 후 현재 초안·다른 버전·최신 원본과 비교할 수 있습니다. 저장 버전을 수정하려면 **이 버전으로 새 초안**을 만듭니다.
5. **인쇄 / PDF 저장**을 누르고 브라우저에서 PDF 저장 대상을 선택합니다. 용지 A4, 배율 100%, 여백 없음, 머리글/바닥글 끄기를 권장합니다. 화면 확대·축소는 인쇄 배율에 영향을 주지 않습니다. 미리보기와 PDF는 동일한 페이지 블록과 한글 폰트를 사용합니다.

## 채용공고에서 지원까지

1. **채용공고 → 채용공고 등록**에서 기업·제목·직무와 JD 원문을 입력합니다. 미기재 날짜·처우는 비워 둡니다. URL은 저장/원문 열기 용도이며 크롤링하지 않습니다. 동일 URL 또는 기업·직무는 경고 후 별도로 저장할 수 있습니다.
2. 공고 상세의 **JD 규칙 분석**은 명시적 제목을 바탕으로 요구사항을 추가합니다. 불확실한 문장은 사용자 확인 필요로 표시합니다. 기존 문구/근거를 삭제하지 않고 중복된 분류·문장만 제외합니다. React/React.js 같은 표기만 정규화하며 React Native와 React, Java와 JavaScript는 구분합니다.
3. **프로젝트 근거 연결**에서 실제 기여·구현·성과를 읽고 검토 여부를 선택합니다. 키워드 후보는 확인 필요, 사용자가 근거를 확인한 항목은 확인됨입니다. 미등록은 현재 기록에서 찾지 못했다는 뜻입니다. 점수나 합격 확률을 만들지 않습니다.
4. 프롬프트에 포함할 JD·직무·기술·경력·프로젝트·성과를 직접 선택합니다. 전체 미리보기와 민감정보 확인 후 복사할 수 있습니다. 선택이 바뀌면 확인도 다시 필요합니다. AI API를 호출하거나 ChatGPT를 자동으로 열지 않습니다. 분석 결과를 직접 입력/수정하면 새 버전으로 보관하며 이전 결과와 나란히 비교할 수 있습니다.
5. **지원 기록 생성 → 이력서 선택 / 복제**에서 초안을 연결합니다. 편집 화면에서 제출본을 확정한 뒤 지원 상세의 **제출 내역 보관**에서 실제 제출본·제출일·방식을 선택합니다. 기업/직무가 다르면 재확인합니다. 문서가 없는 외부 제출도 기록할 수 있습니다. 원본 이력서를 삭제해도 지원에 보관한 문서는 확인/PDF 출력할 수 있습니다.
6. **지원 현황**에서 칸반·테이블·일정을 전환합니다. 드래그 또는 단계 선택창으로 이동하면 변경 사유와 이력을 저장합니다. 지원별 일정의 시간은 선택 입력이며, 완료·수정·삭제할 수 있습니다. 필수 입력은 빨간 별표로 표시합니다.

### 지원 통계 기준

총 지원은 지원일·제출 내역 또는 지원 완료 이후 단계 이력이 있는 고유 지원 ID의 수입니다. 지원 취소는 모든 전환율에서 제외하며 재지원은 별도 건입니다. 서류 통과 누적에는 면접/최종 합격 이력, 면접 진입 누적에는 최종 합격 이력을 포함합니다. 최종 합격·불합격은 현재 단계로 계산합니다. 진행 중·결과 미확정 건은 분모에 포함하며, 분모 0은 데이터 부족입니다. 전환율은 현재까지의 관측치로 합격 가능성을 예측하지 않습니다.

## 개인정보와 보관 범위

- 앱 코드는 공개될 수 있지만, 사용자가 입력한 내용은 각 브라우저의 IndexedDB에만 저장됩니다. 분석·동기화 API, 추적 스크립트, 외부 폰트 요청을 사용하지 않습니다.
- 별도 로그인이나 저장소 암호화가 없습니다. 같은 기기·브라우저 프로필 사용자 및 같은 origin에서 실행되는 코드는 저장소에 접근할 수 있습니다. `ss0900.github.io`의 다른 프로젝트 페이지도 같은 origin임에 유의하세요.
- 저장소는 주소(origin)별로 분리됩니다. localhost, 127.0.0.1, 포트가 다른 개발 주소, GitHub Pages는 별개입니다. 데이터는 JSON으로 옮겨야 합니다.
- 브라우저 데이터 삭제, 저장소 정리, 시크릿 창 종료로 기록이 유실될 수 있습니다. 로컬 저장은 백업을 대신하지 않습니다. 서비스 워커/설치형 오프라인 앱은 아직 구현하지 않았습니다.
- 이름·연락처·내부 프로젝트 정보를 `src/`, `public/`, 테스트 파일에 넣지 마세요. 다운로드 파일은 암호화되지 않습니다. GitHub에 올리지 마세요.
- `/references/`, `/private/`, `/backups/`, `.env*`, 빌드·테스트 산출물은 `.gitignore`로 제외합니다. Vite 개발 서버도 참고자료/개인 폴더의 파일 접근을 차단합니다. 원본 참고자료는 수정하지 않았습니다.
- 외부 링크는 http/https만 허용하고 사용자 문장은 React 텍스트로 렌더링합니다. 파일/이미지 업로드 대신 자료 URL을 저장하며 자동으로 외부 자료를 불러오지 않습니다.
- 공개 포트폴리오에는 별도로 선택·검토·승인한 정적 파일만 사용합니다. URL 분리는 인증이 아닙니다. 같은 브라우저 프로필 또는 같은 origin의 코드가 로컬 저장소에 접근할 수 있다는 점은 동일합니다.

## GitHub Pages 배포

대상 저장소: <https://github.com/ss0900/career-os>

배포 주소: <https://ss0900.github.io/career-os/>. 이번 Phase 4 변경은 로컬에만 적용했으며 배포는 사용자가 Push한 뒤 실행됩니다.

Pages Source는 이미 GitHub Actions로 설정된 상태를 전제로 합니다. 재설정 명령은 필요 없습니다. `vite.config.ts`의 `base`는 `/career-os/`이며, `#/career`, `#/projects`, `#/settings` URL의 직접 접근과 새로고침을 지원합니다.

워크플로는 `main` Push 또는 `workflow_dispatch` 시 설치 → 타입 검사 → 린트 → 단위 테스트 → 빌드 → Playwright 테스트 → `dist/` 업로드 → 배포를 수행합니다. PR에서는 검사만 실행합니다. 배포 권한은 배포 job에만 부여합니다. [Vite 배포 문서](https://vite.dev/guide/static-deploy.html)와 공식 [checkout](https://github.com/actions/checkout), [setup-node](https://github.com/actions/setup-node), [upload-pages-artifact](https://github.com/actions/upload-pages-artifact), [deploy-pages](https://github.com/actions/deploy-pages) 사용법을 기준으로 구성했습니다.

Phase 1 배포와 기존 워크플로를 유지했습니다. 다음 Git 변경 명령은 **사용자가 직접 실행**합니다. 실행 전 현재 브랜치와 파일 목록을 확인하세요.

```powershell
git status --short --branch
git check-ignore references/wanted_resume_01.png references/wanted_resume_02.png references/wanted_resume_03.png references/wanted_portfolio.pdf private/pdf-tools backups/example.json
git ls-files -- references private backups .env
git add README.md package.json package-lock.json vite.config.ts portfolio.html src tests
git diff --cached --name-only
git diff --cached --check
git commit -m "feat: add interview practice and approved portfolio exports"
git push origin main
```

- `status`: 현재 브랜치와 변경 파일 확인
- `check-ignore`: 참고자료·개인 폴더가 제외되는지 확인
- `ls-files`: 개인 자료가 이미 추적되는지 확인(현재 작업 기준 출력 없음)
- `add`: 구현 파일만 명시적으로 staging
- `diff --cached`: 커밋될 파일과 공백 오류 확인
- `commit`, `push`: Phase 4 변경 커밋 및 원격 `main`으로 전송

staging 목록에 개인 자료가 보이면 커밋하지 말고 제외 상태를 먼저 수정하세요. 참고자료가 이미 추적되는 상황에서는 사용자가 해당 경로에 `git rm --cached`를 적용해야 합니다(원본은 보존). 원격이 이후 변경되어 Push가 거부되면 강제 Push하지 말고 변경 상태를 먼저 확인하세요.

Push 후 [Actions](https://github.com/ss0900/career-os/actions)의 **Verify and deploy Career OS** 실행에서 build/deploy 성공을 확인합니다. 실제 원격 배포 성공 여부는 로컬 검사로 확인할 수 없습니다.

## 테스트 범위

- Vitest: DB 재접속 후 유지, CRUD, 경력 삭제 시 연결 해제, 백업 왕복, 잘못된 버전·중복 ID·고아 관계·URL·기간 거절, 용량 제한, 복원 실패 롤백, 실제 데이터 집계
- Playwright: Chromium 데스크톱/모바일 화면, 프로필·경력·프로젝트 CRUD, 새로고침 유지, 검색/필터, 백업 다운로드/취소/복원, 잘못된 파일, 긴 텍스트, 텍스트 안전 렌더링, 미저장 변경 확인, axe 자동 접근성 검사
- Phase 2 Vitest: 원본/제출본 보존, 초안 수정·복제·삭제, 동시 버전 번호, 오래된 탭 저장 충돌, 실제 v1 스키마 업그레이드, v1/v2 복원과 전체 롤백, 품질·비교·페이지 분할
- Phase 2 Playwright: 작성기 자동 저장, 선택·정렬·섹션·보충 정보, 불변 버전 비교, 최신 백업 다운로드/복원, 이동 보호, 접근성, 긴 한글 문서의 다중 페이지 A4 PDF 생성 및 크기·페이지 수 검사
- Phase 3 Vitest: JD 분류·정규화·후보 비교·확정 근거 보존, 단계 이력 원자성, 삭제 후 제출 증빙 보존, 일정 CRUD, 통계, 기존 DB 업그레이드, 최신 백업 왕복 및 실패 롤백
- Phase 3 Playwright: 공고 작성/수정→요구사항 검토→프로젝트 근거 연결→프롬프트/수동 분석→제출본 연결→칸반/표→일정→원본 이력서 삭제 후 제출 PDF, 모바일 및 접근성, 미저장 이동 보호·다중 탭 충돌, 격리된 브라우저의 실제 v1/v2/v3 IndexedDB → v4 업그레이드
- Safari/Firefox, 실제 모바일 기기, 화면 읽기 프로그램 수동 검사 및 원격 GitHub Actions 실행은 별도 확인 대상입니다.

이력서 이미지 3장과 16쪽 포트폴리오 PDF를 확인했습니다. 프로필/핵심역량을 먼저 보여주고 회사 아래 프로젝트를 연결하는 계층, 역할·기술·기여·성과의 분리, 문제→기술 선택→해결→결과→회고 순서, 상세 설계 자료 링크 보관을 Phase 1 모델에 반영했습니다. 원본 이름·연락처·프로젝트 문구·수치·브랜드 디자인은 앱에 복사하지 않았습니다.

Phase 4는 위의 경험 구조를 상세 프로젝트 문구로 확장했습니다. 음성 인식·음성 합성·유료 AI 자동 평가·계정 동기화는 포함하지 않았습니다. 월간 달력과 이미지 백업 일괄 재연결은 후속 개선 후보입니다.

## 면접 준비 사용 순서

1. **면접 준비 → 기업별 면접 준비** 또는 공고/지원 상세의 면접 준비 링크에서 기업을 선택합니다. 함께 검토할 프로젝트를 선택하면 당시 JD·확정 근거·프로젝트·경력·제출본·지원 단계·일정을 복사합니다. 제출본이 없어도 시작할 수 있습니다.
2. 질문 은행에서 유형·직무·기업·프로젝트·미답변·복습·즐겨찾기를 필터링합니다. 생성 질문은 규칙 기반이며 직접 수정하거나 추가할 수 있습니다.
3. **STAR 답변 작성**에서 상황·과제·행동·결과·회고, 자유 답변, 요약을 작성합니다. 0.5초 뒤 자동 저장하며 실패 시 입력을 유지합니다. **답변 버전 생성**으로 고정 복사본을 만들고 과거 버전을 비교하거나 최신 답변으로 지정합니다.
4. **모의 면접 시작**에서 유형·난이도·개수·프로젝트·JD 포함·기술 질문 비율을 선택합니다. 기술/프로젝트 심층 면접은 기술 질문, 인성 면접은 기타 질문만 사용합니다. 조건에 맞는 질문이 부족하면 개수·비율을 조정해야 합니다. 질문을 임의로 만들어 채우지 않습니다.
5. 한 질문씩 답변하고 꼬리질문을 추가합니다. **최신 지정 답변 불러오기**는 사용한 버전 ID와 문구를 세션에 복사합니다. 답변 시간은 보이는 탭에서 측정하며 마지막 약 2초의 차이가 있을 수 있습니다. 새로고침 후 **시작 / 이어하기**를 눌러 다시 측정합니다.
6. 질문별 자체 평가·개선사항·복습 표시와 회고를 저장합니다. 반복 취약은 2점 이하 자체 평가 또는 복습 표시가 2회 이상인 질문입니다. 복습 해제는 질문 수정에서 할 수 있습니다. 실제 면접은 **실제 면접 회고**로 구분하며 자동 시간 측정은 하지 않습니다.
7. ChatGPT 프롬프트에서는 자료를 개별 선택하고 전체 내용을 읽은 뒤 민감정보 확인을 체크해야 복사할 수 있습니다. AI API 호출과 외부 사이트 자동 열기는 없습니다. 결과는 직접 입력해 보관합니다.

## 포트폴리오 작성과 공개

1. **포트폴리오 만들기**에서 현재 프로필·경력·프로젝트 또는 기존 이력서를 복사합니다. 이력서의 짧은 문구와 독립적으로 상세 설명을 편집할 수 있습니다. 원본은 변경하지 않습니다.
2. 프로젝트의 배경·문제·개인 역할·기술 선택·아키텍처·구현·문제 해결·결과·회고를 작성하고 표시 순서를 정합니다. `references/wanted_portfolio.pdf`의 정보 구조만 참고했으며 원본 문구·이미지는 사용하지 않았습니다.
3. 모든 공개 섹션과 경력·프로젝트·이미지는 기본 해제 상태입니다. **공개 제목은 항상 포함**됩니다. 연락처는 원본에서 자동 복사하지 않으므로 공개용 이메일을 직접 입력하고 연락처 섹션을 선택합니다.
4. 현재 브라우저의 미리보기에는 공개 선택한 항목만 표시됩니다. 실제 외부 공개가 아닙니다. 이미지별 공개 승인과 대체 텍스트도 필요합니다.
5. **공개 미리보기와 JSON 확인 완료**와 **최종 승인**을 거쳐 **승인한 정적 파일 내보내기**를 누릅니다. 공개 내용이 바뀌면 확인이 해제됩니다. ZIP에는 `portfolio/portfolio.json`과 승인 이미지 파일만 포함되며, 출처 ID·면접 답변·지원 기록·원본 이력서·비공개 필드는 포함하지 않습니다. 승인 당시 정적 데이터는 내보내기 이력에 남습니다.
6. 다운로드한 ZIP을 검토하고 `portfolio` 폴더를 `public/portfolio`에 배치합니다. 승인한 파일만 직접 staging하고 Commit·Push합니다. 초안 수정은 게시한 파일에 자동 반영되지 않으므로 변경 시 다시 내보내야 합니다.

공개 페이지: **<https://ss0900.github.io/career-os/portfolio.html>**. 기본 저장소에는 공개용 개인 데이터가 없습니다. `portfolio.html`은 별도 Vite 진입점이며 `src/public-portfolio.tsx`에서 정적 JSON만 읽습니다. 개인 DB/Provider를 import하거나 열지 않습니다. 프로젝트 상세와 이미지·링크도 승인된 파일만 사용합니다. 공개 파일을 두지 않으면 미게시 안내만 표시됩니다.

사용자가 승인한 ZIP을 직접 풀어 배치한 뒤 실행하는 예시입니다. 일반 앱 코드 커밋과 별도로 검토하세요.

```powershell
git status --short -- public/portfolio
git add public/portfolio
git diff --cached --stat
git diff --cached -- public/portfolio/portfolio.json
git commit -m "content: publish approved developer portfolio"
git push origin main
```

공개를 철회하려면 사용자가 `public/portfolio/portfolio.json`과 관련 이미지 파일을 삭제한 변경을 커밋·푸시해야 합니다. Git 과거 커밋과 이미 다운로드된 파일까지 회수되는 것은 아닙니다. 공개 전 회사 정보·저작권·내부 자료 여부를 확인하세요.

## 이미지 보관 및 복원 정책

- PNG·JPEG·WebP만 지원합니다. SVG/HTML과 손상된 이미지는 거절합니다. 파일당 3MB, 1,600만 픽셀, 포트폴리오당 보관 이미지 총 30MB로 제한합니다. 브라우저에서 다시 인코딩해 EXIF 등 원본 메타데이터를 제거합니다.
- 이미지 Blob은 IndexedDB에 저장하고 앱에서는 object URL로 미리보기합니다. 공개되지 않은 외부 이미지를 자동 요청하지 않습니다. 제목·설명·대체 텍스트·공개 여부는 JSON 백업에 포함하지만 **이미지 본문은 Base64로 포함하지 않습니다.** JSON 한도는 20MB를 유지합니다.
- **이미지 별도 백업**은 해당 포트폴리오의 이미지 파일 ZIP을 내려받습니다. 비공개 이미지도 포함하므로 Git에 올리지 마세요. JSON 복원은 기존 Blob을 비웁니다. ZIP에서 이미지를 꺼내 각 항목의 **이미지 파일 다시 연결**로 등록하고 공개 여부를 다시 확인하세요. 파일이 없는 공개 이미지는 정적 내보내기를 차단합니다.
- 이전 공개 이력과의 연결을 위해 초안에서 제외한 이미지의 Blob은 포트폴리오 삭제 전까지 보관합니다. 포트폴리오 삭제는 로컬 이미지와 승인 이력도 삭제하지만 이미 게시한 GitHub 파일은 바꾸지 않습니다.

## Phase 4 검증 범위

- Vitest: 질문 생성·답변 버전 불변성·동시 편집·세션/복습 원자성·원본 삭제 보호·조건별 질문 선택·선택 정보 프롬프트·공개 필드 허용 목록·승인 일치·이미지 누락 차단·ZIP·v1~v4 복원·v3 업그레이드·전체 롤백
- Playwright: JD 준비→STAR 버전→세션/꼬리질문/피드백/이어하기→복습, 포트폴리오→이미지 검증→공개 승인→ZIP→독립 공개 렌더링, 모바일·axe 접근성, 격리된 브라우저 v1/v2/v3→v4 업그레이드
- 공개 페이지 테스트에서는 IndexedDB 접근 시 오류를 발생시키며, 공개 렌더링이 개인 저장소에 접근하지 않는지 검사합니다. 테스트 데이터는 가상 자료만 사용합니다.

유료 API·DB·호스팅·도메인을 추가하지 않아 월 0원 운영을 목표로 합니다. 실제 사용 시 GitHub 계정의 Pages/Actions 사용 한도·과금 설정은 사용자 계정 기준으로 확인하세요. 외부 AI API나 유료 동기화 기능을 추가하는 경우에만 별도 비용 검토가 필요합니다.
